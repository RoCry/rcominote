# 实际boot：先加载recovery，失败分支调用ROM入口

2026-10-12。仅静态分析已双覆盖读回、头/正文checksum通过的[3672 B boot](boot-complete.md)，SHA256 `73a199d17490d5ae9e35e466b4ad8fafaa0757fb4a1ae7e79b5c90f90e4cb054`。不执行固件、不改MMIO、不触发恢复模式。以下地址为实际load base `0x01010000`。

## 入口与加载对象

- `01010038..50`：设置SP、清BSS，间接跳到literal `01010501`；`01010500`直接分支到 `01010298`。入口参数r2保存在r6，影响param0/param1的先后顺序；其ROM调用方参数语义未完整确认。
- `0101029e..aa`调用初始化，非零返回转失败分支 `01010414`。
- `010102ea..0346`尝试param偏移 `1000/3000`，映射到`12000000`，以 `010106a8`校验ACPT/FVER。该校验要求ACPT magic、前`2e4`字节CRC与尾word匹配，以及随后FVER magic、`7c`字节CRC匹配；CRC函数从ROM表`0x1b8`取指针。失败会更换param和模式，不证明备用param实际有效。
- `010103c0..d0`调用映射函数：slot0、NOR offset`4000`、CPU base`11000000`、r3来自分区属性bit0。**这一级的正常加载对象是recovery，不是system `24000`。** 后续应用选择应继续在recovery中查。
- `01010d90..b2`实际映射地址为 `(0x08002060 + slot) << 3`，即slot0寄存器`40010300/304`；写CPU base OR`0xf`及物理offset，r3非零时offset置bit31。CPU base低于`18000000`时调用cache刷新。这里建立了实际boot中的映射实现，不是参考SDK公式直接代入设备读取。

## ACTH验收和交接

`010103d4..03fa`比较两个ACTH magic；读取头长（+24），经ROM表`0x1c8`所指函数计算头校验，要求返回`ffffffff`。`0101043e..50`以头长定位正文、+18取正文长度、+1c取存储checksum，要求正文函数结果加存储值=`ffffffff`。这些静态算术与已恢复recovery头校验相容；尚未读出ROM函数本体。

校验失败在`010103fc..0414`或`01010452..5a`记录 `hd err` / `dat err`，进入共同失败路径。通过后以 `11000000 + header_size`作为向量基址，`01010478..7a`调用`01010056`，后者从向量加载SP、从+4取复位入口并BX。不是直接使用ACTH头entry字段进行跳转。

**另有非标准头路径，不能描述成“任何坏magic都必然被拒绝”。** `01010488..04c2`允许若干非ACTH/零前缀布局走向量检查：要求复位入口落在`10000000..11ffffff`且Thumb位为1；通过后交给同一向量跳转。此路径没有经过上面的ACTH头/正文checksum分支，但未知ROM更早检查与完整恢复链，不据此推断安全启动已关闭或任意镜像可刷。

## 带adfu日志的失败/请求路径

- 主流程`010102bc..02de`读index3保留寄存器，随后清零；若高16位=`4252`且bits8..15=`01`，直接进入`01010414`。对应此前[应用重启ADFU标记](application-reboot-path.md) `42520100`，两端现在能由实际代码对上。
- getter/setter `010106f8/01010708`计算 `(0x1000300c + index) << 2`，index3为`4000c03c`，index2为`4000c038`。
- `01010414`先调用`01010c70(1)`设置`40068000`低位/bit4，再尾调用`0101022c`。
- `0101022c..025a`记录地址`01010075`处的 `adfu`，等待后将index2寄存器bit0置1，最终从ROM表地址`0x19c`取函数指针并BX。**这是已定位的实际ROM交接调用点；ROM目标地址、本体、USB枚举、命令和可退出性仍未知。**

## 对用户目标的意义

备用槽4KiB全FF，没有有效参数副本。因此不能从上述重试分支推断本机已有
可用的参数回退；没有实机执行失败切换。

设备自身boot确实有早于应用的recovery校验和ROM失败路径，且与应用ADFU标记闭合。仍不能宣布“刷坏后一定能救”：boot/param本身损坏时是否还能到达这里、ROM独立入口、USB物理可用性、工具写入范围和官方镜像恢复尚未实测。当前最有价值的下一份内容是完整recovery及其实际系统选择/升级逻辑；不用先试刷来验证这些静态问题。

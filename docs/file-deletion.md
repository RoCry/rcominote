## Response and actual-firmware scope

Official `sendCommand` registers an opcode handler before writing. A matching
validated response resolves `{success:true,data:payload}`; duplicate responses
are ignored after completion. `deleteFile` passes through generic success/error
without checking deletion status. Framing validation is separately provided by
`V8` `[219336,219782)`; see [common ACK boundary](cli-capabilities.md#ack-and-error-contract).
Therefore an empty response, or byte00, has no delete-specific success meaning
established by this app source. Preserve raw response and call it
`response_received`, not proof of deletion.

[Actual dispatcher](vendor-dispatch-followup.md#command-to-call-map) independently
routes0d at1000b4c6 to1009ee42 with payload pointer/length. That existing evidence
does not establish the callee's accepted names, unlink result, response timing
or durable storage semantics. No new callee expansion was needed for the
source-backed contract; later hardware acceptance is scoped separately below.

## Explicit CLI contract

These are conservative host policy and observable acceptance criteria, not
claims that the official app enforces the same checks:

1. Require exact device serial and `--confirm-delete NAME` equal to the requested
   name. Validate before connecting; read and compare actual serial before any
   destructive request. Device selection alone is not identity verification.
2. Require observed idle state and a successfully terminated complete file list
   containing exactly one matching name. Unknown state, list failure/truncation,
   absent target or duplicate name must stop before0d. This is not an atomic lock
   against physical recording controls or other clients.
3. Send exactly one0d request with that ASCII name. No wildcard, batch expansion,
   implicit delete after download, or automatic retry.
4. Record matching reply separately from a second complete file list. Only a
   complete post-list without the target establishes
   `scope=listed_recording_absence` (with
   `verification=absent_from_complete_file_list`).
5. Timeout, disconnect, malformed reply/list or failed post-readback leaves the
   destructive outcome unknown. A still-present name fails verification. Do not
   convert ACK, capacity change or connection loss into success; do not retry an
   uncertain delete on a fresh connection.

List absence does not prove secure erasure, durable deletion across restart,
identity of underlying file bytes, or absence of hidden/non-recording files.
The124 retained [recovery SD bridge files](recovery-complete.md) are not an
implicit cleanup target; a name absent from the normal list cannot satisfy the
precondition above. Serial and confirmation reduce accidental targeting but
do not provide cryptographic authentication or a protocol transaction ID.

## Adjacent commands remain separate

Binding/unbinding, formatting and factory reset have different effect and
completion contracts. In particular, official RESET12 means **factory reset**,
not an ordinary reboot or independently established hardware escape. The app's
write-only success and expected disconnect do not prove reset/unbind completed.
This deletion slice adds no implementation or execution approval for them.
